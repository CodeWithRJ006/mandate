I reviewed the actual GitHub repo, README, evaluation harness, tests, API routes, architecture notes, and commit history. I’m going to answer this as though I’m a Razorpay Buildathon reviewer deciding whether your project deserves to move forward.

My verdict

Yes — I would shortlist this project.

But I would not yet call it a guaranteed winner.

My reviewer score would be around 8.2/10, with a realistic chance of making a finalist shortlist depending on the quality of the other submissions.

The reason I would shortlist it is that there is substantially more here than “AI + nice dashboard.” The repository contains a deterministic fulfillment engine, ECDSA signing/verification, nonce/expiry handling, an evaluation harness with 45 cases and stratified 70/30 splitting, a live verification API, and an explicit production-scalability discussion.

What would make me notice this submission

1. The problem is very Razorpay-relevant.

You're not making a generic chatbot or AI wrapper. You've framed the problem around financial liability created by autonomous agents after authorization: the agent gets approval for one thing, but fulfillment can drift in SKU, quantity, or amount. That is a much stronger fintech/agentic-commerce problem than many hackathon ideas.

The README clearly maps it to an AI Risk Manager with detector → verifier → responder responsibilities.

As a reviewer, this is exactly the sort of framing I'd want.

2. You made the important decision deterministic.

This is one of the strongest parts.

You use the LLM to generate/represent agent behavior, but the actual financial decision is made through deterministic logic:

amount tolerance
SKU similarity
quantity matching
mandate expiry
nonce replay
cryptographic signature verification

That architectural choice is much more convincing for a payment-risk system than asking an LLM to decide whether a ₹150 discrepancy is fraudulent. The core engine explicitly performs those checks.

3. You actually thought about false positives vs false negatives.

This is probably the most mature part of your submission conceptually.

The README doesn't simply say “100% accuracy.” It explains the tradeoff and acknowledges that lowering the threshold can improve FPR while causing fraud to slip through. You even document the iPhone 15 Pro → iPhone 13 Mini substitution example and explain why you chose a 0.60 live threshold.

That is risk-engineering thinking, not just demo-building.

4. Your evaluation approach is better than average hackathon work.

You created 45 cases across different categories, including legitimate variance, threshold boundaries, fee padding, SKU substitution, quantity manipulation, expired mandates, and nonce replay. You then use a stratified split to keep categories represented in the held-out set.

That tells me the builder understands that a risk system needs adversarial and boundary testing, not just happy-path screenshots.

5. The Git history shows iterative hardening.

This is actually impressive.

Your latest commits are not all “add feature X.” A lot are corrections around:

threshold calibration
held-out evaluation
FPR interpretation
edge cases
disabled-state UX
NaN/negative amounts
input handling
API consistency
documentation accuracy

The current repo shows 45 commits, with multiple successive evaluation and correctness fixes.

That looks much better to me than a repo with one giant commit containing a polished demo.

But here is what would stop me from giving you a 9.5+

There are some real weaknesses, and these are important.

1. Your documentation currently has a technical inconsistency

This is the biggest thing I would fix before submission.

Your current architecture tradeoff document says the prototype uses a Sørensen–Dice similarity threshold of >0.85, while the actual current policy engine defaults to 0.80, and your live /api/verify route explicitly passes 0.60.

Even worse, the unit-test message still says:

Minor typo ... (>0.85)

while the implementation's default is now 0.80.

A Razorpay engineer reading the repo may immediately think:

“Which threshold is actually the source of truth?”

That creates unnecessary doubt.

Reviewer reaction

I'd write:

Good engineering, but documentation/configuration consistency needs tightening.

This is fixable and shouldn't hurt you much if corrected before judging.

2. Your public /api/verify isn't actually performing the cryptographic verification you claim

This is more serious.

Your README positions cryptographic verification as part of the verification flow. But /api/verify imports and invokes evaluateFulfillment() and computes similarity/amount variance, yet it does not call verifyMandate() in that route.

So your architecture is effectively:

signature verification exists in the project

but the publicly documented verification endpoint is primarily doing:

amount + SKU + quantity evaluation

rather than:

cryptographic verification + fulfillment evaluation

That's a discrepancy I would absolutely notice during technical review.

This is the kind of thing that could turn a “wow, strong system” into a “good prototype, but claims exceed implementation” judgment.

3. Your “Razorpay integration” is more simulated than the README's headline can initially imply

Your architecture notes are commendably honest about this.

You explicitly say production would need things such as HSM/KMS, asynchronous queues, proper identity, and regulatory chargeback integration.

That's good.

However, the current project is still primarily a prototype/simulation of the recourse layer, not a real production Razorpay payment flow.

For example, the malicious fulfillment is intentionally generated as a demonstration fixture with a ₹150 padded amount.

That is perfectly acceptable for a hackathon.

I would simply make the presentation extremely clear:

“We built the risk/recourse decision layer around the payment flow; settlement rails themselves are simulated.”

That's stronger than making a reviewer discover the distinction themselves.

4. Your LLM isn't really the impressive part — and that's okay

You use Groq/Llama 3.3 70B for agent generation and telemetry.

But the actual cleverness of the project is not the LLM.

It's:

AI agents can act autonomously → therefore authorization and fulfillment can diverge → therefore deterministic cryptographic + policy verification is needed.

That's your story.

Don't spend 70% of your presentation talking about Groq.

A Razorpay engineer will probably care much more about:

“How do you prevent a merchant/agent from changing what was authorized?”

than

“Look, we used Llama 3.3 70B.”

5. Your dataset is still small

You have 45 evaluation cases, with 13 held out in the current setup.

For a hackathon, that's fine.

For a real risk system, it's tiny.

And your README actually admits that the held-out result has small-sample variance. That's good scientific honesty.

But don't present:

“100% recall”

as though that proves real-world fraud detection.

Present it as:

“100% recall on our adversarial held-out benchmark.”

That distinction makes you sound much more technically mature.
